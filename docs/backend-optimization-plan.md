# Nail Mind 后端与 AI 试戴优化方案

> 用途：会议评审稿  
> 范围：埋点、AI 试戴、运营后台、Go + MySQL 重构  
> 核心原则：不停服推翻重写，优先解决数据可靠性和任务不丢失问题。

## 1. 当前架构

```text
Android / 运营端 / 商家端
              ↓
          FastAPI
   ├── SQLite 业务数据
   ├── BackgroundTasks 试戴任务
   ├── 服务器本地图片目录
   └── 百炼 qwen-image-2.0-pro

小红书采集 / OpenClaw 分析作为独立运营能力运行。
```

当前业务已经能够完成款式浏览、AI 试戴、收藏、预约、埋点和运营分析，但基础设施仍偏单机 Demo 形态。

## 2. 主要问题

### 2.1 埋点

- 款式曝光按“接口返回”计数，不是卡片真正进入屏幕可视区域。
- 客户端上报失败后没有离线队列和重试机制。
- 事件 ID 由服务端生成，无法完整防止客户端重复上报。
- 事件表和日聚合指标在同一个请求内同步更新，增加接口延迟，并存在并发丢计数风险。
- 事件名和 payload 缺少版本化 Schema，后续客户端升级容易产生口径不一致。

### 2.2 AI 试戴

- FastAPI `BackgroundTasks` 依赖当前 API 进程，容器重启时正在执行的任务可能中断。
- 任务缺少完整的超时、重试、限流、熔断和死信队列。
- 重新生成时可能命中原结果文件，需要重新设计缓存键和款式版本。
- 手图、款式图和结果图依赖服务器本地磁盘，换机、扩容和多 Worker 部署不方便。
- 没有系统记录百炼请求 ID、模型版本、单次耗时、重试次数和估算成本。
- 甲长和甲型界面已取消，但旧字段仍存在于任务模型中，应停止继续扩散。

### 2.3 运营和商家后台

- 款式改名、换图、上下架缺少完整审计记录和版本回滚。
- OpenClaw 建议需要绑定真实证据帖子、采集时间、数据量和置信度。
- 采集、OpenClaw 分析和运营采纳应设计为可追踪的任务流程，不应直接自动修改商品。
- 商家申请应有待审核、通过、拒绝、撤销等明确状态和操作人记录。
- 缺少 AI 试戴成功率、P95 耗时、百炼错误率、积压任务数和成本监控。

## 3. 目标架构

```text
Android / 运营端 / 商家端
              ↓ HTTPS
            Go API
   ├── 鉴权与 RBAC
   ├── 款式、收藏、预约
   ├── 埋点接收
   ├── 运营与商家接口
   └── AI 任务管理
        ↓              ↓
      MySQL       Redis + Asynq
                         ↓
                   Go AI Worker
                         ↓
              百炼 qwen-image-2.0-pro
                         ↓
                    阿里云 OSS

小红书采集服务 → OpenClaw 分析服务 → Go API / MySQL
```

### 组件边界

| 组件 | 职责 |
|---|---|
| Go API | 接收请求、鉴权、校验参数、写业务数据、创建任务、查询状态 |
| MySQL | 保存用户、款式、预约、任务、埋点、审计和运营结果，作为最终可信数据源 |
| Redis + Asynq | 任务排队、延迟重试、并发限制、分布式锁和短期缓存 |
| Go AI Worker | 下载输入图、调用百炼、校验结果、上传 OSS、更新任务 |
| OSS | 保存款式图、用户手图和 AI 结果图 |
| OpenClaw | 分析小红书趋势和站内埋点，输出带证据的运营建议 |

## 4. 埋点优化

### 4.1 事件模型

每条事件至少包含：

```text
event_id          客户端生成的 UUID，用于去重
event_name        受控的事件名
schema_version    事件结构版本
user_id           已登录用户
anonymous_id      未登录设备标识
session_id        会话 ID
style_id/store_id 业务对象
source_page       页面
source_channel    入口或渠道
app_version       App 版本
occurred_at       客户端发生时间
received_at       服务端接收时间
payload_json      受 Schema 约束的附加数据
```

### 4.2 可靠性

- Android 使用 Room 建立本地待上报队列。
- 支持批量上报，网络恢复后指数退避重试。
- MySQL 对 `event_id` 建立唯一索引，重复事件返回成功但不重复计数。
- 原始事件只追加，日聚合指标由异步消费者生成。
- 每日定时从原始事件重算聚合表，作为数据校正机制。

### 4.3 核心漏斗

```text
真实可见曝光
  → 款式点击
  → 收藏
  → 试戴开始
  → 试戴完成 / 试戴失败
  → 预约创建
  → 商家确认
  → 到店完成
```

曝光必须由客户端在卡片进入可见区域并满足最小停留时间后上报。

## 5. AI 试戴优化

### 5.1 可靠任务流程

```text
1. API 验证用户、款式和手图
2. MySQL 创建 tryon_job，状态为 queued
3. 事务提交后将 job_id 写入 Redis/Asynq
4. Go Worker 领取任务并将状态改为 processing
5. Worker 从 OSS 读取手图和款式图
6. 调用百炼 qwen-image-2.0-pro
7. 校验返回图片的大小、格式和可解码性
8. 上传结果至 OSS
9. MySQL 更新 completed 和结果地址
10. 写入 tryon_complete 埋点并通知客户端
```

### 5.2 任务状态

```text
queued → processing → uploading → completed
                   └→ retrying → processing
                   └→ failed
                   └→ dead_letter
```

- 任务必须支持幂等，Worker 重复消费不得生成多条记录。
- 重试仅用于超时、限流和临时 5xx，参数错误、欠费和非法图片直接失败。
- 建议最多自动重试 2 次，超过后进入死信队列等待运营重放。

### 5.3 缓存键

```text
SHA256(
  hand_image_hash
  + style_image_version
  + model_name
  + prompt_version
)
```

“重新生成”需要增加 rerender nonce，明确跳过原缓存。

### 5.4 OSS 存储策略

```text
styles/{style_id}/{version}.png       款式图，可公开读取
hands/{user_id}/{image_id}.jpg        用户手图，私有
tryon-results/{user_id}/{job_id}.png  试戴结果，私有
merchant/{merchant_id}/...            商家图片
```

- 私有图片使用短期签名 URL。
- 用户手图设置生命周期自动清理，并支持用户主动删除。
- MySQL 仅保存 object key、哈希、大小、类型和版本，不保存图片二进制。

## 6. 运营后台优化

### 6.1 款式管理

- 款式资料和图片使用版本号，支持预览、发布和回滚。
- 上下架操作必须记录操作人、原值、新值、时间和原因。
- 商家只能查看已授权门店的商品和预约，不能读取平台趋势和全局埋点。

### 6.2 OpenClaw 建议

每条建议必须展示：

- 建议款式名称和图片。
- 真实小红书原帖、作者、链接和互动量。
- 采集时间、关键词、样本量和过滤条件。
- 站内曝光、点击、收藏、试戴和预约数据。
- OpenClaw 结论、理由、置信度和建议动作。

建议默认只进入待审核状态，需要运营人员确认后才能转为上架、加推或下架操作。

## 7. Go + MySQL 重构范围

### 建议使用 Go 重构

- 用户鉴权和 RBAC。
- 款式、收藏、门店和预约。
- 运营和商家管理接口。
- 埋点接收和聚合任务。
- AI 试戴任务 API。
- Go AI Worker，因为当前仅调用百炼 HTTP API，没有 Python 本地推理依赖。

### 保持独立服务

- 小红书账号登录与数据采集。
- OpenClaw 运行时。

这些服务通过内部 API 或任务队列向 Go 后端提交标准化结果，不直接操作核心业务表。

## 8. 渐进迁移计划

### 阶段 0：基线与备份

- 冻结当前 API 路径和 JSON 字段，生成 OpenAPI 合约。
- 备份 SQLite、图片和服务器配置。
- 补齐登录、款式、试戴、收藏、预约和运营接口回归测试。

### 阶段 1：MySQL + OSS

- 设计 MySQL Schema、索引、外键和审计表。
- 全量迁移 SQLite 数据，校验表数、行数和关键关联。
- 将本地图片同步到 OSS，并回填 object key。
- FastAPI 先切换至 MySQL，客户端不变。

### 阶段 2：Redis + Go AI Worker

- 引入 Redis 和 Asynq。
- 使用 Go Worker 替代 FastAPI `BackgroundTasks`。
- 完成幂等、缓存、重试、死信队列和任务监控。
- 保持现有客户端查询接口兼容。

### 阶段 3：Go API 渐进替换

建议顺序：

```text
埋点接收
→ AI 任务 API
→ 款式和收藏
→ 预约
→ 运营和商家端
→ 鉴权
```

通过反向代理按路径切换流量，每迁移一个模块就做数据对账和回滚演练。

### 阶段 4：运营分析与可观测性

- 完成真实可见曝光和 Android 离线埋点队列。
- 建立试戴成功率、P95 耗时、队列积压、百炼错误码和成本仪表盘。
- 为 OpenClaw 提供标准的小红书证据和站内指标接口。

## 9. 上线与回滚策略

- 禁止一次性全量重写后直接切换。
- 新旧 API 保持路径和响应结构兼容。
- MySQL 迁移期先做只读校验，再做短时停写切换。
- 图片迁移期保留本地路径回退能力。
- 每个新模块必须支持一键切回 FastAPI。
- 上线前保留完整 SQLite、OSS 清单和 MySQL 备份。

## 10. 验收指标

### 可靠性

- API 或 Worker 重启后，已创建的试戴任务不丢失。
- 重复消费同一 job 不产生重复记录和重复计费。
- 埋点在弱网恢复后可以补传，且 `event_id` 不重复计数。

### 性能

- 普通 API P95 延迟小于 300ms，不包含 AI 生成时间。
- 埋点批量接口不阻塞用户业务请求。
- 试戴 Worker 并发数可配置，不超过百炼限流阈值。

### 业务

- 运营端可查看真实漏斗、试戴成功率和失败原因。
- 所有款式修改均可审计和回滚。
- OpenClaw 建议可追溯到真实帖子和站内数据。
- 商家账号无法访问平台运营趋势和其他门店数据。

## 11. 会议需要确认的决策

1. 是否确定为 `Go API + Go AI Worker + MySQL + Redis/Asynq + OSS`。
2. 是否允许渐进迁移，而不是一次性推翻 FastAPI。
3. 用户手图和试戴结果的保留时间。
4. 试戴自动重试次数和单日成本预算。
5. OpenClaw 建议是否始终需要人工审核后才能执行。
6. 新架构的分阶段上线时间和人员负责边界。
