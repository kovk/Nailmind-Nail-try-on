# NailMind 方案设计文档

本文说明当前工作区里的实际方案。`app/`、`backend/`、`web-admin/` 和 `inference/` 分别对应 Android 客户端、业务后端、后台 Web 和 GPU 推理服务。文中没有特别标注的能力，均以仓库现状为准。

| 状态 | 含义 |
|---|---|
| 已实现 | 仓库中已有页面、接口、数据结构或测试 |
| 依赖环境 | 代码已经接入，但运行需要模型密钥、社区登录态或 GPU |
| 后续演进 | 当前版本尚未落地，只说明下一步改造方向 |

## 1. 项目背景与需求

### 1.1 项目背景

美甲消费有一个很直接的问题：款式图很好看，用户仍然不知道放到自己手上是什么效果。肤色、手型、甲面长度和拍摄光线都会改变最终观感。用户在线上反复挑选，真正做决定时还是要靠想象，试错成本最后落到到店环节。

平台运营面对的是另一类信息差。社区里的颜色、工艺和风格变化很快，平台内部每天也在产生曝光、点击、收藏、试戴和预约数据。人工整理这些信息需要时间，等趋势变得明显时，合适的运营窗口可能已经过去。

NailMind 从这两个问题出发。产品用 AI 试戴帮助用户确认效果，同时用 Agent 读取外部趋势和站内经营数据。门店商家提供真实的价格、库存、档期和服务，把线上的选择接到线下预约。

### 1.2 简要需求分析

产品涉及消费用户、门店商家和平台运营三个角色。他们使用同一套款式和门店数据，但关注点不同。

| 角色 | 实际需求 | 对应能力 |
|---|---|---|
| 消费用户 | 快速找到喜欢的款式，看到本人上手效果，并能继续预约 | 小美导购、双路 AI 试戴、收藏、门店咨询和预约 |
| 门店商家 | 维护真实可售的款式，处理用户咨询和预约 | 门店资料、价格、库存、档期和预约管理 |
| 平台运营 | 及时发现流行方向，判断款式表现，调整平台供给 | NailClaw、Ops Assistant、款式生产、审核和质量管理 |

需求分成两条线。用户从找款、咨询和试戴走到预约；商家提供供给，运营再根据社区趋势和站内数据调整款式。用户产生的点击、收藏、试戴和预约记录把两条线接了起来。

### 1.3 产品目标

NailMind 希望把美甲选择变成一个可以验证的过程。用户上传一次手图，可以同时查看 GPU 推理结果和生图模型生成结果；第一张成功图片生成后立即展示，另一条线路继续运行。用户看完结果后可以收藏款式或直接预约门店。

三个 Agent 各管一段流程。小美理解用户偏好，NailClaw 观察社区趋势，Ops Assistant 分析站内转化。它们都读取平台款式，但数据范围和写入权限不同。运营人员可以从建议回到原帖、款式或站内指标，不必只看模型给出的结论。

### 1.4 模型调研与选择

团队用相近的手图、款式图和提示条件测试了多类图像模型，观察款式还原、手部保持、速度、国内接入和单次成本。

| 方案              | 实际观察                                       | 选择结果                   |
| ----------------- | ---------------------------------------------- | -------------------------- |
| 豆包图像模型      | 响应快，部分结果会让皮肤发亮，手部质感不够稳定 | 用于前期对比               |
| Nano Banana       | 生成质量好，审美表现稳定                       | 国内代理与费用需要额外处理 |
| Qwen Image 2.0 Pro | 效果与速度比较均衡，国内 API 接入方便         | 用于趋势候选款脱敏图生成   |
| GPT Image 2       | 手部和背景保持较好，适合按参考图做局部编辑     | 作为试戴生图线路           |
| 独立 GPU 局部推理 | 甲面区域可控，能保留原手图的大部分结构         | 作为可控推理线路           |

生图线路使用 GPT Image 2，App 对用户显示"生图模型生成结果"。GPU 线路负责甲面定位和局部编辑。两条线路同时运行，用户可以直接比较结果。三个 Agent 的默认语言模型是 `qwen3.7-plus`；NailClaw 另外调用 Qwen Image 2.0 Pro 生成候选款商品图。

## 2. 总体方案与技术架构

### 2.1 整体思路

产品由 Android 用户端、商家 Web 工作台和运营 Web 工作台组成。用户端负责找款、试戴和预约；商家端维护门店供给并承接服务；运营端管理款式、趋势和经营策略。

技术设计主要解决试戴和 Agent 两类问题。试戴系统同时调用独立 GPU 服务和 GPT Image 2。三个 Agent 分别实现自己的 Planner、模型适配器、Memory 和工具层，并遵守相同的输入校验和权限约定。

| 产品部分 | 主要能力 |
|---|---|
| 用户端 Android App | 首页、搜索、款式详情、收藏、AI 试戴、小美、门店咨询、预约和个人记录 |
| 商家端 Web 工作台 | 入驻、门店资料、款式供给、价格、库存、档期、咨询和预约查看 |
| 运营端 Web 工作台 | 款式生产、生命周期、商家审核、试戴质检、趋势分析和经营策略 |
| AI 能力 | GPU 局部推理、GPT Image 2 试戴生图、Qwen 图像生成、Qwen3.7-Plus 多模态理解与结构化输出 |

### 2.2 三角色业务架构

用户端围绕决策展开。款式发现和小美缩小选择范围，AI 试戴确认上手效果，收藏和预约承接后续动作。商家端提供价格、库存和档期，运营端则根据趋势证据和站内数据管理款式与策略。

三端的主要流程如下：

| 角色 | 业务过程 |
|---|---|
| 用户 | 浏览或咨询小美，选择款式，上传手图，查看两张试戴结果，收藏或预约 |
| 商家 | 提交门店资料，维护款式与可售状态，查看咨询和预约，完成到店服务 |
| 运营 | 导入和审核款式，查看趋势与经营诊断，确认策略，观察后续转化 |

### 2.3 系统分层

| 层次 | 组成 | 负责内容 |
|---|---|---|
| 交互层 | Android App、运营与商家 Web 工作台 | 页面交互、结果展示和任务轮询 |
| 业务层 | 用户、款式、门店、供给、预约、试戴任务 | 权限检查、业务规则和数据聚合 |
| Agent 层 | 小美、NailClaw、Ops Assistant | 理解目标、组织上下文、调用工具和生成结果 |
| 模型层 | GPU 推理、GPT Image 2、Qwen 图像模型、Qwen3.7-Plus | 图像推理、图像生成和多模态理解 |
| 数据层 | 业务数据、行为事件、图片、趋势证据 | 保存业务状态和分析依据 |

客户端调用统一业务接口。业务层创建试戴任务、准备 Agent 上下文并检查权限，模型层专注图像和语言推理。各模型通过适配层接入，客户端看到的接口保持稳定。

| 场景 | 模型或能力 | 用途 |
|---|---|---|
| 款式素材预处理 | SAM3、TPS 展平 | 款式入库时提取五指透明甲片素材 |
| GPU 试戴 | YOLO11s-seg、甲片配准、局部融合或修复 | 在用户手图中定位甲面并贴合五甲片素材 |
| 生图试戴 | GPT Image 2 | 以手图为主图，把款式图中的美甲迁移到甲面 |
| Agent 推理 | Qwen3.7-Plus | 意图理解、多模态分析、趋势建议和经营诊断 |
| 趋势候选图 | Qwen 图像模型 | 根据社区款式证据生成新的脱敏商品图 |
| 试戴质检 | Qwen3.7-Plus 多模态 | 比较输入与结果，输出质量评分 |

### 2.4 行为与趋势数据

用户的点击、收藏、试戴和预约会写入行为事件。运营聚合这些事件后，可以看到款式漏斗和日趋势。NailClaw 采集的社区帖子会保存关键词、图片、互动量和来源。外部证据说明近期流行方向，站内数据说明这些方向进入产品后的真实表现。

## 3. 双路并发 AI 试戴

### 3.1 为什么同时生成两张图

两条路线解决的问题不同。GPU 路线只在甲面附近工作，位置更可控；GPT Image 2 直接编辑完整画面，成图通常更自然。后端同时发起两次推理，哪一张先成功就先给用户看。单个服务出错时，另一条路线仍可完成本次试戴。

每次试戴只有一个主任务，主任务下固定有两个结果槽位：

| provider | App 标题 | 生成方式 |
|---|---|---|
| `gpu` | GPU 推理结果 | 独立 GPU 试戴接口 |
| `gpt-image` | 生图模型生成结果 | GPT Image 2 API |

### 3.2 并发流程

```text
App 创建试戴任务
  -> 后端准备公共输入
  -> GPU 分支准备五甲片素材并调用推理服务
  -> GPT Image 分支提交手图和款式图
  -> 任一分支成功后立即返回首张结果
  -> 两个分支结束后保存完整任务状态
```

后端创建主任务后，用线程池分别调用 GPU 和 GPT Image。完成回调按真实结束顺序处理，先完成的线路先写结果。五甲片素材只在 GPU 分支内准备，因此素材处理或 GPU 服务异常不会挡住 GPT Image 分支。

两条线路各自保存生成状态、结果图片、耗时和错误原因。GPU 失败时，GPT Image 任务继续运行；GPT Image 调用失败时，GPU 任务继续运行。两条线路都失败后，整次试戴才会显示失败。

### 3.3 任务状态

一次试戴由一个主任务和两个模型结果组成。主任务保存公共输入并同时启动 GPU 与 GPT Image 两个子任务，各分支自行准备所需材料。任意一张图片成功，主任务就进入可查看状态；两条线路结束后，本次任务才算全部处理完毕。

公共准备阶段发生错误时，系统会终止这次试戴。进入并发生成后，两条线路分别更新自己的结果，互相不等待，也不会互相覆盖。

当前任务由 FastAPI 进程内的后台任务和线程池执行，任务状态会写入数据库，但执行本身还没有交给独立队列。服务进程在生成期间退出时，任务需要人工重试。把执行器迁到持久化队列属于后续演进，不应当算作当前完成项。

### 3.4 首张图片耗时

运营端记录用户等到第一张可用图片的时间。接口字段是 `firstResultDurationMs`，计算方式是：

```text
firstResultDurationMs = min(所有成功结果的 duration_ms)
```

GPU 先完成时记录 GPU 的耗时，GPT Image 先完成时记录生图线路的耗时。第二张图片完成后，首图耗时保持原值。两条线路都失败时，该字段为空，失败次数单独统计。

这个指标更接近用户感受到的等待时间。运营看板可以继续保留各 provider 的耗时，用来比较模型表现，但首页平均试戴耗时只使用首张图片耗时。

### 3.5 App 展示

试戴结果页使用横向翻页组件。第一张图片完成后，App 立即进入结果页，同时继续轮询另一条线路。第二张图片完成后，它会自动加入翻页列表。

每张图片下方显示来源标签，分别是"GPU 推理结果"和"生图模型生成结果"，右侧显示当前页码。用户可以保存当前图片，也可以继续查看款式、收藏或预约同款。

结果页只展示已经成功生成的图片。某条线路失败时，另一张成功图片照常使用；两条线路都失败时，App 返回重新上传和生成的提示。

### 3.6 GPU 推理路线

款式入库时，推理服务先用 SAM3 从款式图中分割指甲，再通过门槛检查、mask 内缩和 TPS 展平生成五张透明甲片。运营复核后的素材包由后端保存，用户发起试戴时不再临时从完整款式图里裁甲片。

用户试戴时，GPU 服务用 YOLO11s-seg 定位手图里的真实甲面，再读取款式对应的五甲片素材。系统根据每根手指的位置、方向和甲面大小做几何配准，把素材融合回原图。仓库提供的生产环境示例使用 `local_inpaint` 修复局部边缘；`reference_local_edit` 和 FLUX.2 Klein 是可选或评测中的后端，不是默认链路。

这条路线尽量保留原手图的手型、肤色、姿态和背景。生成自由度集中在甲面附近，适合强调款式位置与手部身份保持。

处理步骤如下：

1. 校验手图和已复核的款式素材包。
2. 用 YOLO11s-seg 定位手图中的可见甲面。
3. 按拇指、食指、中指、无名指和小指选择甲片。
4. 完成缩放、旋转和透视配准。
5. 在甲面附近做局部融合和边缘修复。
6. 将编辑区域合回原分辨率手图，并返回推理指标。

### 3.7 GPT Image 2 路线

GPT Image 路线把用户手图作为主图，把款式图作为参考图。提示词要求模型只迁移甲面上的颜色、图案、甲型、长度、装饰和光泽，并保留原来的手型、肤色、姿势、背景、光线和构图。模型仍可能重绘非甲面区域，所以结果会进入后续质检。

生图服务采用异步任务接口。业务层提交两张图片后轮询任务状态，下载完成图片，并把鉴权、限流、内容检查和服务异常转换成用户可以理解的提示。

### 3.8 结果质检

质检模型同时读取原手图、目标款式图和生成结果，检查以下六项：

| 检查项 | 判断内容 |
|---|---|
| 款式还原 | 颜色、纹理、装饰和整体风格是否接近目标款式 |
| 甲面贴合 | 图案是否落在甲面内，边缘是否自然 |
| 手指数量 | 是否出现多指、少指或明显结构错误 |
| 皮肤保持 | 肤色和皮肤质感是否出现明显变化 |
| 姿态保持 | 手型、方向和构图是否被大幅改动 |
| 背景保持 | 原背景是否被无关内容替换 |

质检结果用于运营抽查和模型对比。用户页面先展示成功图片，质检在后续任务中完成，避免延长首图等待时间。

## 4. 三个 Agent 的统一设计

### 4.1 分工和边界

三个 Agent 都会接触款式数据，但各自处理的问题不同。小美服务消费用户，NailClaw 读取外部社区，Ops Assistant 读取站内经营数据。三者分别实现自己的提示词、Planner 和工具，不能越过业务接口直接写数据库。

| Agent | 主要输入 | 负责的判断 | 可以调用的工具 | 最终输出 |
|---|---|---|---|---|
| 小美 | 用户对话、偏好、最近手图、在架款式 | 用户想做什么，是否需要看手图，哪些款式更合适 | 手图分析、知识检索、款式检索、App 页面入口 | 回复、手型分析、款式卡片、详情或试戴入口 |
| NailClaw | 社区帖子、图片、互动量、发布时间、平台款式库 | 样本能否说明趋势，趋势是否已有相似款 | 社区采集、证据检查、款式库匹配、候选款生成、脱敏图生成 | 原帖证据、趋势判断、现有款加推建议或新款候选 |
| Ops Assistant | 曝光、点击、收藏、试戴、预约、用户偏好分组、款式状态 | 漏斗问题在哪里，哪些款值得加推或降权 | 指标查询、首页推荐、款式状态、人群推荐组 | 经营回答、待确认方案、执行结果、后续效果复盘 |

三个 Agent 都使用 Qwen3.7-Plus，但用法不同。小美用它处理模糊意图、手图理解和对话表达。NailClaw 用它做多模态趋势判断。Ops Assistant 先由规则代码算出指标和动作，再让模型把结果写成运营人员容易理解的说明。

### 4.2 共同的运行约定

一次 Agent 请求会经过下面这条链路：

```text
请求入口
  -> 上下文与短期记忆
  -> Planner 判断任务并准备计划
  -> Qwen3.7-Plus 理解图片或生成结构化结果
  -> Tool Manager 调用获准的业务工具
  -> 结果校验与业务状态写入
  -> 页面需要的文字、卡片和操作入口
```

Planner、LLM Adapter、Tool Manager 和 Memory 是一套共同约定，不是四个由三个 Agent 直接共用的单例组件。每个 Agent 在自己的目录中实现这些职责。Planner 决定本轮需要哪些数据和工具，模型适配器处理鉴权、请求和结构化结果，工具层限制可执行动作，Memory 只保存当前业务需要复用的上下文。

款式查询、指标计算、证据阈值、权限和写操作都由普通代码完成。模型处理文字和图片理解，不能绕过工具层改变款式或推荐位。

三个 Agent 的记忆范围也按业务需要区分：

| Agent | 当前记忆内容 | 持久数据放在哪里 |
|---|---|---|
| 小美 | 最近 8 条有效对话、用户偏好、当前手图标识和上一轮手图分析 | 用户资料、手图和行为记录 |
| NailClaw | 保留 Memory 接口，当前不额外保存会话状态 | 趋势主题、原帖证据、候选款和建议记录 |
| Ops Assistant | 最近的分析与执行摘要 | 日指标、推荐组、动作结果和事件记录 |

小美和 Ops Assistant 支持流式输出。服务端发送 `status`、`delta`、`result`、`done` 四类事件。`delta` 负责逐段显示文字，页面最终以 `result` 中的结构化数据为准。即使模型流式输出中断，服务端也会发送结束事件，页面不会一直停在加载状态。

### 4.3 小美

小美的一次对话分为意图路由、知识补充、工具执行和结果组装四步。

第一步是意图路由。系统先处理试戴、预约、收藏、DIY、身份询问等明确表达，再用词语和槽位识别场景、颜色、甲型和风格。只有语义比较模糊、规则无法确认时，才调用 Qwen3.7-Plus 解析意图。用户只说"推荐一款"时，Planner 会先追问偏好；用户已经给出"通勤、显白、短甲"这类条件时，Planner 直接进入推荐流程。这样可以减少不必要的模型调用，也让常见入口响应更快。

第二步是知识补充。小美的知识库收录色彩、甲型、工艺、场景、人群和护理等内容。检索器把用户当前问题、最近对话和用户偏好合在一起，进行中文短词切分和同义词扩展，再按正文、标签和知识槽位计算相关度。Planner 取分数最高的知识片段，并把其中的颜色、甲型和风格词加入后续检索条件。知识库只提供推荐依据，真实款式仍从平台款式库读取。

第三步是工具执行。有手图时，多模态工具先判断图片中是否有清晰手部，再分析肤色明度、冷暖倾向、手指比例、甲床和可见指甲数量。模型只能从平台规定的甲型和风格集合中返回结果，置信度不足或未检测到手部时，App 会引导用户重新上传。有效手图分析会短时缓存，重复咨询时可以直接复用。

款式工具只查询已上架且有展示图的真实款式。推荐器把用户明确说出的条件、手图结论、个人偏好和知识库扩展词放在一起评分。颜色、甲型和风格有明确要求时采用严格匹配，其余情况按名称、标签和款式属性计算相关度。接口返回少量候选，并附带款式名称、图片、推荐原因、标签和详情入口。

第四步是组装结果。接口返回自然语言回复、意图、手图分析、推荐款式和 App 入口。入口是结构化对象，例如款式详情、试戴上传、收藏或预约。App 直接读取目标页面和款式编号完成跳转，不需要从回答文字里猜用户下一步要去哪。

模型服务暂时不可用时，小美仍能完成明确意图路由、知识检索和款式匹配。手图分析失败时，它会说明当前照片没有分析成功，并让用户重试或先用文字描述偏好。

### 4.4 NailClaw

NailClaw 的处理链路从社区证据开始。采集器按关键词读取近期图片帖子，统一标题、作者、图片、发布时间和互动量字段，过滤非美甲内容、过期内容和重复帖子。系统先扩大采集范围，再选出较有代表性的帖子读取详情，最后按猫眼、法式、新中式、渐变、钻饰等款式特征聚类。

社区热度进入模型前会先经过证据门槛。当前规则至少要求 2 条不同帖子和 1 张可复核图片，最高点赞要达到 100，综合互动要达到 500。综合互动的计算口径是点赞数加 2 倍收藏数，再加 3 倍评论数。证据不足时，系统只保留观察结论，不会生成候选款。

通过基础门槛后，Qwen3.7-Plus 最多读取 4 张帖子图片和对应文字。模型需要返回甲面是否清晰、有效参考图数量、跨帖子款式一致性和门店复刻难度。只有有效参考图不少于 2 张、甲面可见度不低于 0.70、跨帖一致性不低于 0.60、商业复刻度不低于 0.65，并且模型明确判断为可运营趋势时，Planner 才会继续生成款式建议。模型调用失败时，本轮分析会标记为不可用，系统不会拿点赞最高的帖子直接代替趋势判断。

形成趋势判断后，Tool Manager 先匹配平台款式库。标签、名称、颜色和甲型已经命中现有款式时，输出的是现有款加推或恢复建议，同时带上该款的曝光、点击、试戴和预约数据。没有匹配款时，系统才创建新的候选款，避免同一种风格重复入库。

新候选款会先进入待审核状态。原帖图片只保存在 `sourcePosts` 中，供运营复核证据，候选款的展示图不会直接使用原帖。生图工具从最多 3 张社区参考图提取甲面款式，用 Qwen 图像模型重新生成合成模特手和干净背景的商品图，并去掉人物身份、首饰、纹身、文字和水印。生成成功后，候选款才会带上新的展示图进入运营页面。

NailClaw 的输出包含趋势名称、趋势说明、置信度、原帖证据、库内匹配结果、候选款信息和下一步建议。运营可以从结果回到每条原帖，也能看出系统为什么选择加推现有款或创建新款。

### 4.5 Ops Assistant

Ops Assistant 先读取款式日指标，再计算点击率、试戴率、预约率和综合表现分。综合分会提高收藏、试戴和预约的权重，避免只按曝光量排序。Planner 目前支持五类任务：自然语言查询、自动发现问题、人群偏好分析、生成待确认方案和执行后评估。

自然语言查询会先定位问题中提到的款式、标签和指标，只把相关数据交给 Qwen3.7-Plus。用户问某款点击率时，回答只围绕该款和点击率展开。自动发现模式则由规则检查几类常见断点，例如高曝光低点击、有点击无试戴、试戴后无预约。模型负责把规则结果写成运营说明，不会改动原始指标。

生成方案时，Planner 根据真实指标构造动作参数。表现较好的款式可以进入首页前排，高曝光低互动的款式会被建议取消首页推荐，连续没有点击、试戴和预约的款式会进入下架观察。人群策略先读取匿名偏好组合，再按标签命中和近期转化表现生成首页推荐组。每个推荐组都包含目标人群、款式顺序、流量比例、投放天数和观察指标。

写操作只有三类：修改款式状态、调整首页推荐位、创建或更新人群推荐组。运营点击确认后，执行接口才会给动作加上 `operatorConfirmed` 并交给 Tool Manager。工具层还会再次检查款式是否存在、是否已上架、是否有展示图，以及排序、周期和流量参数是否合法。场景分类始终由款式标签决定，Agent 只能调整首页推荐，不能直接把款式写入"通勤"或"约会"等场景分类。

Ops Assistant 的流式接口先用规则层完成指标、问题和动作计算，再让 Qwen3.7-Plus 流式生成解释文字。模型服务不可用时，规则层的查询、诊断和待确认动作仍然可以正常返回。执行结果会记录成功数量和具体消息，评估模式再读取之后的曝光、点击、收藏、试戴和预约数据进行复盘。

### 4.6 输出校验与调用约束

三个 Agent 都对模型输出做结构检查。JSON 解析失败、字段不在允许范围或工具名不存在时，本轮调用会回到规则结果或停止继续执行。模型返回的款式名称和建议不能直接替代数据库对象，工具层会重新查询真实款式并校验状态。

| 约束位置 | 处理方式 |
|---|---|
| 模型输入 | 只传当前任务需要的对话、图片、指标和候选款，控制上下文范围 |
| 模型输出 | 使用固定 JSON 字段，对枚举、分数、数量和工具名再次检查 |
| 数据读取 | 小美读取在架款式，NailClaw 读取社区证据和款式库，Ops 读取聚合经营数据 |
| 数据写入 | NailClaw 只生成待审核候选，Ops 写操作需要平台运营确认 |
| 失败处理 | 小美使用规则回复，NailClaw 停止生成候选，Ops 返回规则层诊断 |

### 4.7 三个 Agent 怎样交换数据

NailClaw 发现社区里正在升温的颜色和工艺，并附上原帖证据。运营确认后，新方向才进入候选款和款式库。小美根据用户偏好和手图推荐已经上架的款式。用户随后产生的浏览、收藏、试戴和预约会进入站内指标，Ops Assistant 再判断哪些款式值得继续加推。

外部趋势、平台供给和用户反馈最后都落到款式编号上。运营可以沿着候选款、正式款式和行为指标检查建议执行后的结果。

## 5. 数据与效果验证

### 5.1 数据流向

用户浏览款式后，点击、收藏、试戴和预约会成为站内行为记录。商家维护的价格、库存和档期决定款式是否能在门店成交。NailClaw 保存社区趋势证据，Ops Assistant 再把外部趋势与站内表现放在一起分析。

一次试戴会保存两条模型结果。系统知道哪张图来自 GPU，哪张图来自 GPT Image，也会记录各自的完成状态和耗时。App 用这些结果完成横向翻页，运营端则读取第一张成功图片的耗时。

运营可以按款式编号查看一个社区趋势入库后有没有获得点击、试戴和预约，据此判断上新或加推是否有效。

### 5.2 指标口径

用户侧关注的是选择过程有没有变简单。系统会观察用户是否愿意发起试戴、第一张图需要等待多久，以及看完试戴后是否继续收藏或预约。

模型侧会分别观察 GPU 和 GPT Image 的生成成功率、耗时与图片质量。两条线路都成功时，用户可以比较两张图；其中一条失败时，另一条线路仍然可以完成这次试戴。

运营侧关注的是趋势发现和经营判断是否更快。NailClaw 的建议要能找到原始帖子，Ops Assistant 的诊断要能对应真实漏斗，执行上新或加推后还要继续观察后续变化。

### 5.3 验证方法

双路试戴测试会覆盖几种真实情况：GPU 先完成、GPT Image 先完成、两条线路同时成功，以及其中一条失败。每种情况下都要检查 App 展示、横向翻页、首图耗时和失败提示。两条线路都失败时，用户可以重新生成。

图像质量使用固定手图和固定款式对比。GPU 与 GPT Image 接收相同输入，再从款式还原、甲面贴合、手指数量、肤色、姿态和背景六个方面检查结果。人工对比时隐藏模型名称，减少对供应商的先入判断。

仓库已有基准脚本、推理样例和接口测试，但正式文档不写死演示数据生成的分数。平均耗时、成功率和质量分必须来自同一版本、同一批样本的实际运行记录；没有有效样本时，后台显示"待评测"。

三个 Agent 分别检查各自最重要的能力。小美要理解用户意图并推荐合适款式；NailClaw 的趋势结论要有真实证据；Ops Assistant 的诊断要和站内数据一致。模型可以用不同方式表达，但调用的工具、款式和运营动作需要准确。

## 6. 演示路径

1. 用户在 App 中浏览款式并询问小美。
2. 用户上传手图，后端同时启动 GPU 和 GPT Image 两条线路。
3. 第一张图完成后进入结果页，第二张图随后加入横向翻页列表。
4. 用户从试戴结果进入门店并提交预约。
5. 商家在工作台查看预约和款式供给。
6. 运营查看 NailClaw 的趋势证据和候选款建议。
7. 运营打开 Ops Assistant，查看站内漏斗诊断并确认策略。
8. 运营回到看板，检查加推或上新后的点击、试戴和预约变化。

这条路径覆盖用户决策和运营反馈，也能在一次演示中说明双路试戴、Agent 权限以及数据回流各自做了什么。
