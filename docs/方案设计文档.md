## 1. 项目背景与目标

### 1.1 要解决的问题

| 角色 | 当前问题 | 产品处理方式 |
|---|---|---|
| 消费用户 | 款式图好看，但很难判断放到自己手上的真实效果，也不容易快速选到适合自己的方向 | 小美导购、风格档案、AI 试戴、收藏和预约 |
| 门店商家 | 价格、库存、档期、咨询和预约分散 | 商家工作台统一维护门店供给 |
| 平台运营 | 社区趋势变化快，站内漏斗靠人工整理，动作执行后也不容易复盘 | NailClaw 发现趋势，Ops Assistant 分析转化和执行建议 |

![业务活动图](../assets/uml/01-business-loop.svg)

### 1.2 产品目标

| 目标 | 验证方式 |
|---|---|
| 用户更快看到本人上手效果 | 记录生成耗时和试戴成功率 |
| 用户推荐更贴近手部特征和实际场景 | 检查风格档案、手图分析和推荐回答是否对齐 |
| 当前部署不依赖常开 GPU | GPT Image 2 独立完成试戴生成 |
| 趋势建议可以复核 | 每条建议保留原帖、图片和互动证据 |
| 运营动作可控 | 写操作使用白名单，并由运营确认 |
| 建议执行后可以复盘 | 按款式编号继续观察点击、试戴和预约 |

### 1.3 模型调研与选择

| 方案 | 实际观察 | 当前用途 |
|---|---|---|
| 豆包图像模型 | 响应快，部分结果会让皮肤发亮 | 前期对比 |
| Nano Banana | 生成质量好，国内代理与费用需要额外处理 | 效果对照 |
| Qwen Image 2.0 Pro | 效果与速度较均衡，国内 API 接入方便 | 趋势候选款商品图 |
| GPT Image 2 | 手部和背景保持较好，适合参考图编辑 | 当前试戴主线路 |
| 独立 GPU 局部推理 | 甲面区域可控，但需要单独维护 GPU 实例 | 代码保留，默认停用 |
| Qwen3.7-Plus | 支持文字、图片理解和结构化输出 | 三个 Agent 与试戴质检 |

## 2. 总体架构

### 2.1 三端业务架构

![系统组件图](../assets/uml/02-system-components.svg)

### 2.2 系统分层

| 层次 | 组成 | 职责 |
|---|---|---|
| 交互层 | Android App、运营与商家 Web | 页面交互、流式回复展示、任务轮询、审核确认 |
| 业务层 | 用户、款式、门店、供给、预约、试戴任务、后台概览 | 权限检查、业务规则、状态流转、数据聚合 |
| Agent 层 | 小美、NailClaw、Ops Assistant | 理解目标、准备上下文、调用工具、返回结构化结果 |
| 模型层 | GPT Image 2、Qwen Image 2.0 Pro、Qwen3.7-Plus，保留 GPU 实验线路 | 图像生成、多模态理解、质检和可选本地推理 |
| 数据层 | 业务数据、事件、图片、趋势证据、推荐知识 | 保存状态、分析依据和推荐上下文 |

### 2.3 模型与业务边界

![模型边界组件图](../assets/uml/03-model-boundary.svg)

客户端不直接调用模型服务。底层模型替换时，App 和 Web 接口保持不变。

按当前仓库来看，三端分工已经比较清楚。`app/` 是 Jetpack Compose 客户端，负责用户浏览、试戴、预约和小美对话；`web-admin/` 继续使用原生 HTML、CSS、JavaScript，但已经把后台路径、趋势看板和运营工作台独立出来；`backend/` 则从单一 API 服务发展成业务接口加三类 agent 编排，并通过 HTTP 调用外部推理服务。

## 3. 当前 AI 试戴方案

### 3.1 当前生成时序

![试戴时序图](../assets/uml/04-tryon-sequence.svg)

当前默认主线路是 GPT Image 2。业务后端负责准备手图、款式图、提示词和任务状态，再轮询生成结果。GPU 分支仍保留在代码中，只有 GPU 服务在线且显式启用时才参与生成，日常部署不依赖这条线路。

### 3.2 任务状态

![试戴任务状态图](../assets/uml/05-job-state.svg)

| 当前结果情况 | 用户看到的内容 | 主任务结果 |
|---|---|---|
| GPT Image 2 成功 | 显示一张试戴结果 | 完成 |
| GPT Image 2 失败 | 显示错误并允许重试 | 失败 |
| 显式启用 GPU 实验线路 | 按实际完成情况记录额外结果 | 非默认部署场景 |

异步试戴接口保留了任务制结构，但当前统计口径看的是首张成功结果。这样用户可以先看到第一张可用图，后端再继续补齐其他结果，不必把等待时间拉长。

### 3.3 生成耗时

```text
当前部署的试戴耗时 = GPT Image 2 结果的 duration_ms
```

| 指标 | 口径 |
|---|---|
| 试戴耗时 | 从任务开始到 GPT Image 2 结果完成的时间 |
| 生成成功率 | GPT Image 2 成功任务数除以总任务数 |
| GPU 实验数据 | 仅在显式启用 GPU 时单独记录，不进入默认口径 |

### 3.4 保留的 GPU 实验路线

![GPU 试戴活动图](../assets/uml/06-gpu-activity.svg)

| 后端 | 当前定位 |
|---|---|
| `local_inpaint` | 仓库提供的生产环境示例 |
| `reference_local_edit` | 可选参考图增强线路 |
| FLUX.2 Klein | 评测中的可选线路 |

这套链路保留用于实验和效果对照。由于 GPU 实例平时不开机，产品演示和日常试戴不依赖它。
另外，款式第一次进入试戴时，后端会先生成并缓存甲片素材包，后续同款试戴可以直接复用，避免每次都重新做甲面提取。

### 3.5 GPT Image 2 路线

![GPT Image 2 试戴活动图](../assets/uml/07-gpt-activity.svg)

提示词要求迁移颜色、图案、甲型、长度、装饰和光泽，同时保留手型、肤色、姿势、背景、光线和构图。模型仍可能重绘非甲面区域，因此结果会进入质检。

## 4. 三个 Agent

### 4.1 分工

| Agent | 输入 | 工具范围 | 输出 |
|---|---|---|---|
| 小美 | 对话、偏好、最近手图、风格档案、在架款式 | 手图分析、知识检索、款式检索、App 入口 | 回复、分析、款式卡片和跳转入口 |
| NailClaw | 社区帖子、图片、互动量、款式库、站内趋势数据 | 采集、证据检查、款式匹配、候选图生成 | 趋势证据、加推建议或新款候选 |
| Ops Assistant | 曝光、点击、收藏、试戴、预约、推荐位状态 | 指标查询、首页推荐、款式状态、推荐组 | 经营诊断、待确认方案和执行结果 |

### 4.2 共同运行约定

![Agent 公共组件图](../assets/uml/08-agent-components.svg)

Planner、模型适配器、Tool Manager 和 Memory 是共同约定，每个 Agent 在自己的目录中实现这些职责。模型不能绕过工具层改变款式、候选款或推荐位。流式接口也做了统一约定，事件顺序固定是 `status`、`delta`、`result`、`done`，其中真正给前端渲染卡片和动作的是 `result`，`delta` 只负责逐字展示过程文本。

### 4.3 记忆和流式输出

| Agent | 短期记忆 | 持久数据 |
|---|---|---|
| 小美 | 最近 8 条有效对话、偏好、手图和上一轮分析 | 用户资料、手图和行为记录 |
| NailClaw | 当前不额外保存会话状态 | 趋势主题、原帖、候选款和建议 |
| Ops Assistant | 最近的分析与执行摘要 | 日指标、推荐组、动作结果和事件 |

![Agent 流式输出时序图](../assets/uml/09-stream-sequence.svg)

这里的记忆更接近业务状态。小美更依赖最近对话、手图和用户档案来保持回答连续；NailClaw 和 Ops Assistant 更关心上一次分析留下的主题、动作和结果，重点放在复盘。

### 4.4 小美

![小美活动图](../assets/uml/10-meimei-activity.svg)

小美现在已经不只是一个问答入口。后端为它补了一套结构化知识库，里面有款式、颜色、甲型、材质、工艺、人群、场景、护理、画像映射、推荐流程、回答模板、评测问题和评分规则。模型不可用时，明确意图路由、知识检索和款式匹配仍由规则完成，不会因为 LLM 失效就整条链路中断。手图无效时，App 会引导用户重传，或者改用文字描述继续推荐。

### 4.5 NailClaw

![NailClaw 活动图](../assets/uml/11-nailclaw-activity.svg)

| 门槛 | 当前值 |
|---|---:|
| 不同帖子数 | 至少 2 条 |
| 可复核图片 | 至少 1 张 |
| 最高点赞 | 至少 100 |
| 综合互动 | 至少 500 |
| 有效参考图 | 至少 2 张 |
| 甲面可见度 | 不低于 0.70 |
| 跨帖一致性 | 不低于 0.60 |
| 商业复刻度 | 不低于 0.65 |

综合互动按“点赞 + 2 × 收藏 + 3 × 评论”计算。候选图不会直接使用原帖人物图，原帖只作为运营复核证据。

这部分和早期版本相比，变化主要有两点。第一，NailClaw 不再按单帖高赞直接推爆款，而是要求跨帖子一致、甲面可见、并且能复刻到商品图。第二，它会先比对站内款式库，命中相似款时给的是加推或恢复建议，不会重复造一个新款。

### 4.6 Ops Assistant

![Ops Assistant 活动图](../assets/uml/12-ops-activity.svg)

| 可写操作 | 约束 |
|---|---|
| 修改款式状态 | 款式必须存在，状态迁移合法 |
| 调整首页推荐位 | 款式已上架并有展示图 |
| 创建或更新人群推荐组 | 排序、周期和流量参数合法 |

场景分类由款式标签决定，Agent 不能把款式直接写入“通勤”或“约会”等分类。

Ops Assistant 现在已经把“能分析什么”和“能改什么”分开了。它可以读取真实经营指标做诊断，也可以生成候选动作，但自动执行只允许低风险白名单，像直接下架、直接改高风险状态这类操作会被工具层拦下。

### 4.7 输出和权限约束

| 位置 | 处理方式 |
|---|---|
| 模型输入 | 只传当前任务需要的对话、图片、指标和候选款 |
| 模型输出 | 固定 JSON 字段，检查枚举、分数、数量和工具名 |
| 数据读取 | 每个 Agent 只读自己的业务范围 |
| 数据写入 | NailClaw 只建待审核候选，Ops 写操作需要运营确认 |
| 失败处理 | 小美回到规则结果，NailClaw 停止建候选，Ops 返回规则诊断 |

这套约束把 agent 放在业务编排层的位置。模型参与决策，但不直接拥有写权限，这也是当前方案里比较关键的一点。

## 5. 数据回流与验证

### 5.1 数据回流

![数据反馈组件图](../assets/uml/13-data-feedback.svg)

候选款、正式款式和行为指标通过款式编号关联，运营可以检查一次上新或加推后的实际变化。

### 5.2 指标口径

| 观察对象 | 指标 |
|---|---|
| 用户 | 试戴发起率、生成耗时、试戴后收藏率、试戴后预约率 |
| 模型 | GPT Image 2 成功率、耗时、款式还原、甲面贴合、手部与背景保持；GPU 实验数据单独统计 |
| NailClaw | 证据完整率、候选通过率、候选入库后的转化 |
| 小美 | 推荐命中场景、风险提示是否前置、是否给出适合理由和避开方向 |
| Ops Assistant | 诊断与真实指标一致性、动作执行结果、执行后变化 |

### 5.3 验证矩阵

| 验证对象 | 场景 | 检查内容 |
|---|---|---|
| 当前试戴 | GPT Image 2 成功、失败、超时和重试 | 结果展示、生成耗时和错误提示 |
| GPU 实验线路 | GPU 在线且显式启用 | 不影响默认试戴，结果与错误单独记录 |
| 图像质量 | 固定手图和固定款式 | 六项质检和隐藏模型名称的人工对比 |
| 小美 | 明确意图、模糊意图、有效手图、无效手图 | 路由、推荐、降级和 App 入口 |
| NailClaw | 证据不足、已有相似款、新趋势 | 停止建候选、加推建议、新候选 |
| Ops Assistant | 查询、诊断、生成方案、确认执行、复盘 | 指标准确性、动作白名单和权限 |

仓库现在的验证已经不只是一组接口测试。后端有 agent contract tests，专门检查流式事件顺序、NailClaw 的演示隔离、Ops 的白名单边界和小美在模型不可用时的降级行为；`web-admin/` 也补了多组前端契约测试，保证趋势主题、候选款、工作台和指标面板的渲染结构不被随手改坏。平均耗时、成功率和质量分必须来自同一版本、同一批样本；没有有效样本时显示“待评测”。

### 5.4 结果质检

| 检查项   | 判断内容                                   |
| -------- | ------------------------------------------ |
| 款式还原 | 颜色、纹理、装饰和整体风格是否接近目标款式 |
| 甲面贴合 | 图案是否落在甲面内，边缘是否自然           |
| 手指数量 | 是否出现多指、少指或结构错误               |
| 皮肤保持 | 肤色和皮肤质感是否明显变化                 |
| 姿态保持 | 手型、方向和构图是否被大幅改动             |
| 背景保持 | 原背景是否被无关内容替换                   |

质检在生成结果返回后异步执行，不延长用户等待结果的时间。

## 6. 完整演示路径

![完整演示时序图](../assets/uml/14-demo-sequence.svg)

这条演示链路把现在仓库里最重要的更新串到了一起。用户侧从 App 进入，可以先补风格档案，再和小美对话、上传手图、发起试戴、收藏款式并继续预约；后台一侧，NailClaw 负责整理趋势证据和候选建议，Ops Assistant 再结合真实指标给出可执行动作，最终仍由运营确认。

如果从技术亮点看，这一版更值得讲的是三件事已经接上了。第一，试戴主链路已经从依赖常开 GPU 调整成默认走在线图像模型，实验线路继续保留。第二，三个 agent 都有自己的边界、工具和回退逻辑，各自处理对应的问题。第三，评测和验证也从单点效果扩成了试戴结果、agent 决策、前后端契约三层一起看，后续继续补真实数据时可以直接沿用这套结构。
